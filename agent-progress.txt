Swift Deep Research v2 — Agent Progress Log

PROJECT OVERVIEW
----------------
Complete rebuild of an existing macOS 14 / Swift 5.9 single-agent research app into a macOS 26 / Swift 6.2
orchestrator-worker deep research agent. Architecture mirrors Anthropic's multi-agent research system
(orchestrator + parallel worker subagents) with Foundation Models as the on-device orchestrator brain
and Anthropic/OpenAI/Gemini as long-context synthesizers.

CURRENT STATE OF REPO
---------------------
Old single-agent app (~6,235 LOC) still in place. Will be replaced incrementally; legacy files
deleted only after their replacements are wired and the build is green.

Existing dependencies (kept): SwiftSoup, mlx-swift, mlx-swift-examples, swift-markdown-ui,
ollama-swift.

To be added: swift-anthropic, MacPaw/OpenAI, mcp-swift-sdk, firebase-ios-sdk (for Firebase AI Logic
Gemini fallback).

  pyseekdb/fastapi/uvicorn/pydantic. Candidates include the managed venv, every

Session 2026-06-05 — Systematic resilience hardening (branch: main)
================================================================================
Goal: eliminate the whole class of "sidecar won't start / DB returns no sources /
timeouts / web sources fail to read" issues. Ran four parallel subagent audits
(sidecar startup, KB retrieval, network/timeouts, websearch) and fixed the real
bugs they surfaced. Build SUCCEEDED after every batch; sidecar smoke-tested live.

Engine resilience (the big one):
- ResearchEngine.runWorkers used `for try await out in group`, so ANY single
  worker that threw (per-worker tool-call cap, exhausted-retry network drop,
  budget bust) cancelled the whole TaskGroup and ABORTED THE ENTIRE RUN. Now the
  group element is WorkerOutput?; non-cancellation throws are caught, emit a
  .warning, and drop to nil so surviving workers still reach synthesis. Genuine
  CancellationError still propagates.
- WorkerAgent.run: wrapped the hop loop in do/catch (labeled toolLoop). Budget
  caps and transient provider failures now `break` and return partial findings
  instead of throwing. registerToolCall cap is a normal stop, not a fatal error.

Network / timeouts:
- Logging.defaultSession: timeoutIntervalForResource was `timeout*2` (=600s for a
  300s request) — a hard ceiling that killed long deep-research streams mid-flight
  ("network connection lost"). Decoupled: resource defaults to 86_400s; only the
  per-request inactivity window guards liveness. Added browserUserAgent +
  dataWithRetry() (retries transient URLErrors + 408/425/429/5xx, honors
  Retry-After) for the web tools.
- Anthropic + Gemini stream(): inactivity timeout 120s -> 300s (reasoning models
  idle before first token) AND added the pre-response transient-retry loop
  (serverResponded guard so output never duplicates) they previously lacked.
- OllamaClient: per-line JSON now `try?` (one malformed NDJSON line no longer
  aborts the whole stream).
- RetryPolicy.isTransient: added .secureConnectionFailed/.cannotFindHost, excludes
  CancellationError + URLError.cancelled.

Sidecar startup (SidecarSupervisor):
- ensureRunning now coalesces concurrent callers onto ONE launch Task (check+assign
  in a single synchronous actor step) — fixes duplicate launches racing on port 9100.
- terminate() is async (no Thread.sleep blocking the actor's executor).
- runProcess() has a cancellable timeout watchdog (ResumeOnce/TaskHolder); interpreter
  probes use timeout:8 so a wedged pyenv shim can't hang startup forever.
- waitForHealthOrExit polls up to ~90s while the process is alive (cold pyseekdb init
  exceeds 15s — confirmed: live cold start took ~5-8s+).
- installDependencies: removes a partial venv on failure and verifies all four modules
  import before declaring success; bootstrap retries after a 90s cooldown instead of
  latching off for the whole session. launch() tears down the old pipe (no FD leak).
- seekdb_sidecar.py: parent-death watchdog thread self-terminates when the launching
  app exits (getppid()==1) — frees port 9100, fixes orphan/port-conflict after crashes.

KB retrieval:
- seekdb_sidecar.py score: `1.0 - dist` could go negative/NaN (non-cosine distances) →
  mis-sorted, 0%-badged. Now `1/(1+d)` via _distance_to_score → always (0,1], higher=closer.
  VERIFIED live: relevant query 0.738, unrelated 0.503.
- _delete_chunks_of: `include=["ids"]` is invalid and raised → stale/duplicate chunks on
  re-upsert + broken delete. Now `get(where=...)` with no include.
- KnowledgeBaseTool.queryWithRecovery: recovers from HTTP 5xx (cold init) too, retries the
  query 3x w/ backoff, and no longer treats a still-`.launching` supervisor as fatal.
- Zero-hit results now carry a `note` (empty-KB vs no-match, with doc count) the worker reads.

Web source reading:
- WebReaderTool: browser UA (fixes 403/429), dataWithRetry, charset-tolerant decode
  (UTF-8→CP1252→ISO-8859-1), 500→200 char threshold, and replaced the deadlock-prone
  DispatchSemaphore JS bridge with async evaluateJavaScript (+200k innerText cap, stopLoading).
- PDFReaderTool: browser UA + retry, Content-Type guard (HTML-as-PDF), encrypted/locked unlock,
  empty-text guard (scanned PDFs), releases source slot on failure.
- WebSearchTool/DDG: percent-encode the query, actually stop enumeration at limit, browser UA + retry.
- Reddit/Wikipedia/ArXiv: browser UA where needed + dataWithRetry; release source slot on failure.
- SourceCache.normalize: lowercase scheme+host only (path/query are case-sensitive) — no more
  /Page vs /page collisions handing a worker the wrong page.
- AgentBudget.releaseSource(): failed fetches no longer permanently consume a worker's source budget.

Verification: xcodebuild Debug BUILD SUCCEEDED (0 errors/0 warnings in our files) after each batch;
sidecar smoke test confirmed health/upsert/query/score-normalization/re-upsert all work on new code.

CRITICAL FIX: every Qwen tool call failed ("knowledge_base: invalid arguments",
"web_search arguments invalid: The data couldn't be read because it isn't in the
correct format"). See screenshots — 0 successful tool calls on Qwen.
- Root cause: OpenAICompatibleClient.parseEvent only accepted streamed
  function.arguments when it was a String (OpenAI spec: incremental string
  fragments). Alibaba DashScope / Qwen compatible-mode delivers the COMPLETE
  arguments as a JSON *object* in one chunk. The `as? String` cast failed
  silently → no argument delta yielded → the engine assembled an empty string →
  JSONDecoder dataCorrupted ("isn't in the correct format"). Name still came
  through (first delta), so the UI showed the tool firing with empty args.
- Fix: new argumentsFragment(from:alreadyBuffered:) coerces the arguments value —
  String → fragment as-is; JSON object/array → serialize to a JSON string, but
  only as the FIRST payload for that call (object payloads are complete, so this
  avoids double-concatenation if a gateway re-sends). Also default a missing
  tool-call `index` to 0 so single non-streaming-style calls aren't dropped.
- Verified with a standalone Swift harness (/tmp/argtest.swift): string-fragments
  ✅, Qwen object-form ✅ (decodes to valid query), object-resent-twice ✅ (no
  corruption), and the OLD path reproduced the EXACT screenshot error. Both
  web_search and knowledge_base (same empty-args victim) now receive valid args.

Robustness: SSEParser now strips a trailing \r so CRLF gateways still match
"[DONE]" (terminal detection) and JSON payloads carry no stray control char.
Benefits all SSE providers (OpenAI/Anthropic/Gemini/OpenAI-compat).

  in c8f4ffa did not resolve it (user still saw every tool call fail).
  GROUND TRUTH: captured the real Qwen compatible-mode SSE via curl. Arguments
  ARE streamed as normal OpenAI string fragments, BUT every CONTINUATION delta
  carries `id:""` (empty string) instead of omitting the id field:
    d1: id="call_039..", function.arguments="{\"query\": \"Deep"
    d2: id="",           function.arguments="Seek V3 latest news\","
    d3: id="",           function.arguments=" \"limit\": 5}"
  parseEvent resolved the id as `entry["id"] as? String ?? buffered` — and ""
  satisfies `as? String`, so continuation fragments were yielded under id "".
  The engine accumulates argumentsJSON keyed by id (currentIndex[id]); there is
  no entry for "", so all fragments after the first were DROPPED. Assembled args
  = "{\"query\": \"Deep" → JSONDecoder dataCorrupted → "invalid arguments" /
  "couldn't be read", for EVERY multi-fragment tool call (all tools).
  FIX: nonEmpty() helper treats a present-but-empty id/name as absent, so the
  buffered call id is reused across fragments and the engine accumulates them on
  one call. Verified by replaying the REAL captured fragments through a faithful
  simulation: OLD → "{\"query\": \"Deep" (decode fails, = user's error); NEW →
  "{\"query\": \"DeepSeek V3 latest news\", \"limit\": 5}" (decodes). The
  object-form coercion from c8f4ffa is kept purely as defensive handling for
  other gateways; it was never the Qwen issue. DeepSeek/Kimi were unaffected
  because they omit id on continuations (nil → buffered) rather than sending "".
